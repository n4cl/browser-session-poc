# コミットメッセージルール

## 参照タイミング

- Gitコミットを作成する直前に参照する。

## 基本方針

- コミットメッセージは `type: 日本語メッセージ` 形式とする。
- `type` は変更の種類を表し、メッセージには更新の目的を簡潔に書く。
- 最優先は、何のための更新かが分かることである。
- コミットメッセージは、そのコミットに含まれるGit管理下の変更だけに言及する。
- 何を変えたかだけで終わらず、差分から明らかでない場合は目的が伝わる表現を選ぶ。
- 差分に含まれない将来案や別の変更に関する話題を含めない。
- セッション中に参照しただけで、当該コミットから追跡できないローカルファイル名、絶対パス、一時ファイル、私的なメモ、記録されていない会話などに言及しない。
- 追加の説明が必要な場合は、コミット本文だけで理解できるように書くか、追跡可能なIssue、PR、ADRなどを参照する。

## 形式

```text
type: 日本語メッセージ
```

変更理由や制約を要約だけでは説明できない場合は、空行を挟んで本文を追加できる。

```text
type: 日本語メッセージ

変更が必要な理由や、差分からは分からない制約を書く。
```

例:

- `feat: ブラウザ操作をセッション単位で分離できるようにする`
- `fix: 切断後にNative Messaging Hostプロセスが残る不具合を修正`
- `docs: 契約と検証に基づく開発方針を定義`
- `chore: 開発環境の設定を更新`
- `refactor: ブラウザ操作の判定処理を整理`
- `test: Native Messagingの異常系テストを追加`

## type

- `feat`: 利用者から見える機能の追加
- `fix`: 不具合の修正
- `docs`: ドキュメントだけの変更
- `chore`: 依存関係、設定などの保守作業
- `refactor`: 外部から見える振る舞いを変えない実装の整理
- `test`: テストの追加、修正、検証コードの改善

複数の`type`にまたがる独立した変更は、可能であればコミットを分ける。一つの目的を実現するためにコードとテストや文書を同時に変更する場合は、主目的を表す`type`を選ぶ。
