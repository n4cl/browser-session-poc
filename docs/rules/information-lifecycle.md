# 情報ライフサイクルルール

## 参照タイミング

- 変更目的や受け入れ条件の正本を決めるときに参照する。
- コード、契約、テスト、文書の食い違いを見つけたときに参照する。
- 変更から得た情報をどこへ残すか判断するときに参照する。

## 基本方針

同じ情報を複数の場所へ複写しない。情報の性質ごとに一つの正本を決め、他の場所からはリンクまたは短い参照だけを置く。

変更固有の目的や検討経緯は、現在状態を表す設計文書やコードへ変更履歴として複写しない。変更から得られた内容のうち、現在も守る必要があるものは契約やテストへ反映し、将来も理由を参照する必要がある設計判断だけをADRへ残す。

## 情報の正本

| 情報 | 主な正本 | 更新する契機 |
| --- | --- | --- |
| プロダクトの目的と長期的な範囲 | README、vision文書 | 目的や対象範囲を変更したとき |
| アイデア、優先順位、探索中の議論 | Issueや利用中の課題管理場所 | 検討や優先順位が変わったとき |
| 一つの変更の目的と受け入れ条件 | Issue、PR、コミットのいずれか一つ | 変更内容について合意が変わったとき |
| 外部契約と永続形式 | Schema、型定義、migration、契約テスト | 境界や互換性を変更したとき |
| 現在の実装と構造 | コード、設定、生成資料 | 実装を変更したとき |
| 長期的に重要な設計判断 | ADRまたは共有する意思決定場所 | 判断を採用、却下、置換したとき |
| 検証結果 | CI、テスト結果、評価結果、監視 | 対象の変更または実行時 |

Issue、PR、ADRなどの具体的な利用先が決まっていない場合でも、正本を一つにする原則は維持する。リポジトリ外に正本を置く判断も許容するが、コードを変更する際に必要な判断は実装から辿れるように参照を残す。

## 変更目的の保存先

- 実装前の検討、優先順位、採用しなかった案を残す必要がある変更は、Issueを正本とする。
- 実装した変更の目的とレビュー上の判断だけを残せばよい場合は、PRを正本にできる。
- 小さく自明な変更は、コミットメッセージを正本にできる。
- 同じ目的や受け入れ条件をIssue、PR、設計文書へ複写しない。

IssueやPRが将来参照できなくなる可能性がある場合や、リポジトリ単体で理解できなければ保守判断を誤る場合は、必要な内容を契約、現在状態の文書、またはADRへ昇格させる。

## 情報の昇格

変更固有の目的や検討結果から、実装後も必要な情報だけを次のように昇格させる。

- 現在も守る振る舞い、不変条件、境界は、契約、Schema、テストへ反映する。
- 現在の構造や利用方法として必要な内容は、コード、設定、生成資料、現在状態の文書へ反映する。
- 将来も理由を知らなければ判断を誤る、長期的に重要な設計判断はADRへ残す。
- 一時的な設計仮説や、価値のなくなった事前設計は、現在仕様として残さない。

ADRは、長期的に重要な判断が初めて発生した時点で `docs/decisions/` または適切な共有場所に作成する。空のディレクトリや雛形は事前に作らない。

## 証拠が食い違った場合

自然言語、契約、テスト、コード、実行結果に対する絶対的な優先順位は設けない。食い違いを見つけた場合は、機械的にどれかを正しいものとして書き換えず、次を明らかにする。

1. どの問いに対する証拠が食い違っているか。
2. 既存バグ、古い契約、誤ったテスト、新しい要求、環境差のどれに当たるか。
3. 現在の挙動を維持、変更、または移行する必要があるか。
4. 判断によって影響を受ける契約、検証、実装、文書は何か。

最終的な判断は、人間が変更目的、互換性、リスク、得られた事実を確認して行う。エージェントは矛盾と選択肢を報告し、判断を暗黙に代行しない。
