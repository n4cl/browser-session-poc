# 開発方針

## 目的

このリポジトリでは、自然言語の仕様書を唯一の正本とせず、現在の挙動を出発点として、変更目的を確認し、契約と検証に基づいて開発を進める。

自然言語は、解決したい問題、利用者の目的、判断理由を伝えるのに適している。一方で、表現に幅があり、コードとの意味的一致を機械的に保証できない。また、実装前には分からなかった制約が実装中や運用中に判明するため、事前設計が常に正しいという前提も置かない。

情報の性質に応じて、自然言語、Schema、制約、テスト、コード、実行結果、運用観測を使い分ける。設計と実装を一度で確定するのではなく、小さな変更と検証から得た事実を次の判断へ反映する。

## この方針の位置付け

「契約と検証に基づく開発」は、業界で確立された単一の開発手法の名称ではない。このリポジトリでは、次の既存の実践を必要に応じて組み合わせる。

- Executable Specification / ATDD: 重要な振る舞いを受け入れテストで表す
- Contract-First Development: 外部との境界をSchemaや明示的な契約で表す
- Docs as Code: 長期的に必要な文書をコードと同じようにレビューする
- Delta Specification: 現在仕様全体を複製せず、今回の変更点を記録する
- ADR: 長期的に重要な設計判断と理由を残す
- Architecture Tests / Fitness Functions: 構造や非機能上の重要な性質を継続的に検証する
- Evaluation-Driven Development: 実装、評価、修正のループで完成度を上げる

これらをすべての変更で要求するものではない。変更のリスクと、守る必要がある性質に応じて必要なものだけを使う。

## 用語

### 変更目的

今回の変更によって解決したい問題、実現したい結果、または確かめたいことを指す。変更ごとに独立した文書を要求するものではなく、差分から自明でなければIssue、PR、コミットなど適切な一つの場所で確認できればよい。

### 契約

システムの境界で、呼び出し側、利用者、保存済みデータ、外部プロセスなどに対して守ると決めた内容を指す。例えば次を含む。

- CLI、API、Native Messagingの入出力
- メッセージ、設定、ファイルなどのSchemaと形式
- 永続データの制約と互換性
- セキュリティ境界と許可する操作
- 外部から観測できる重要な振る舞い

内部関数、クラス構成、一時的な中間データまで無条件に契約として固定しない。内部実装は、外部契約と必要な不変条件を守る範囲で変更できる。

### 検証

目的とした結果、契約、重要な性質が満たされているかを確かめる行為と証拠を指す。テスト、Schema検証、データ制約、型検査、静的解析、実行結果、運用観測、人間による評価などを含む。

テスト結果だけを唯一の合否判定にはしない。自動化できない体験や価値判断は、人間が確認する。

## 開発原則

### 設計は正解ではなく仮説として扱う

実装前の設計と計画は、その時点で得られている情報に基づく仮説である。実装と検証から新しい事実を得たら、設計、契約、検証方法、または実装を見直す。

実装が当初設計と異なること自体を失敗とは扱わない。価値のなくなった事前設計を、現在仕様に見せかけて維持し続けない。

### コードを正解とはみなさない

コードと実行結果は、現在システムが実際に行うことを知るための強い証拠である。しかし、バグや暫定実装を含む可能性があるため、何を行うべきかの正解とは限らない。

現在動いている挙動は、明示的に変更すると決めるまでは後方互換性の初期値として扱う。

### 機械的な保証を優先する

重要な制約は、可能な限り実行可能な形へ落とす。自動化できる制約を注意書きだけで済ませず、Schema、型、データ制約、テスト、静的解析、監視など、制約に適した仕組みで検証する。

一つの検証方法だけで十分とは限らない。重要な性質は、リスクに応じて複数の層で守る。

### 自然言語には理由と境界を残す

自然言語で長期管理するのは、主に問題と目的、外部から観測できる重要な振る舞い、不変条件、境界、設計判断の理由、コードから復元できない背景とする。

コードやSchemaから生成できる情報や、内部処理の逐次説明は、原則として自然言語に重複して保持しない。

### 変更の儀式はリスクに比例させる

小さく可逆的な変更に、詳細な設計書やADRを要求しない。外部互換性、データ損失、セキュリティ、復旧性などに影響する変更では、必要な契約、移行方法、異常系、運用上の検証を明らかにする。

## 運用ルール

- 変更の進め方、リスク判定、完了条件は [`rules/change.md`](rules/change.md) に従う。
- 変更目的、契約、ADRなどの保存先と昇格条件は [`rules/information-lifecycle.md`](rules/information-lifecycle.md) に従う。
- コミットメッセージは [`rules/commit-message.md`](rules/commit-message.md) に従う。

個別機能の仕様、実装の逐次説明、変更ごとの受け入れ条件は、この文書へ複写しない。この文書は、開発方針そのものを変更した場合に更新する。
